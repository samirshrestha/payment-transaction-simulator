# Host

Simulates the single endpoint that receives authorization requests and returns authorization responses. Implements the published ISO 8583/AS2805 standard for message format. Runs as a standalone Kotlin/JVM process, listening as a TCP socket server with one-way TLS (self-signed cert for local dev) — see [ADR-0005](../docs/adr/0005-terminal-host-transport.md).

## Language

**Host**:
The single simulated endpoint that authorizes or declines a transaction directly. Collapses what would, in a real network, be separate Issuer and Acquirer roles into one — this simulator does not model a network hop or an Issuer/Acquirer split.
_Avoid_: Issuer, Acquirer, Network

**Authorization**:
A transaction type that reserves funds against a limit without moving money. Does not complete a transfer on its own.
_Avoid_: Auth (informally fine, but glossary entries use the full term), Hold

**Financial**:
A transaction type that authorizes and completes a funds transfer in a single message, with no separate capture step.
_Avoid_: Purchase, Sale, Completion

**Reversal**:
A transaction that undoes a prior Authorization or Financial transaction that did not complete cleanly (e.g. the Terminal timed out waiting for a response). Reversing an Authorization releases its hold; reversing a Financial undoes a completed transfer. One concept regardless of which it targets — not split into separate "Authorization Reversal" / "Financial Reversal" terms.
_Avoid_: Void, Cancellation

**Transaction**:
The umbrella entity Host tracks through a lifecycle. Has a type (Authorization, Financial, or Reversal) and a status. For v1, status is binary — `Approved` or `Declined` — with no in-flight/pending state, since Host processing is synchronous (request in, response out). More granular states (e.g. distinct timeout or per-field validation-failure states) are deferred.
_Avoid_: Message (that's a wire-format concept, not a domain one)

**Account**:
A simulated record Host holds per PAN, carrying a balance and a limit. Authorization holds funds against the limit without moving the balance; Financial moves the balance directly. This is what gives Host real approve/decline logic (insufficient funds, over limit) instead of an arbitrary rule. See [ADR-0001](../docs/adr/0001-simulated-account-store-for-host-decisioning.md).
_Avoid_: Card (Account is the record Host holds; the card itself isn't modeled)

**STAN**:
System Trace Audit Number (ISO 8583 DE 11). Each Transaction is assigned exactly one STAN when it begins, whichever path it takes (online request, or offline Financial Advice) — a Reversal doesn't get a STAN of its own, it carries the target Transaction's STAN directly, and retries of a Reversal or Advice reuse that same STAN unchanged. Generated by the originator (Terminal), not Host. Host keeps an in-memory STAN → Transaction map, valid indefinitely for the process lifetime — no expiry window in v1 — and uses STAN + Repeat Indicator to detect a retried Reversal or Advice.

**Financial Advice**:
A message from Terminal reporting a Financial transaction that was already approved offline (under Terminal's Floor Limit) — distinct from the online Financial request/response pair. Host cannot decline it; it just applies the Account change (which, realistically, could push a balance negative — that's the risk a floor limit trades for speed, not a bug to prevent). See [ADR-0004](../docs/adr/0004-floor-limit-offline-financial-advice.md).
_Avoid_: treating Advice like a request Host can approve/decline

**Repeat Indicator**:
The ISO 8583 MTI's origin digit (odd value = repeat, even = original) — the standard mechanism Terminal uses to mark a retried Reversal or Financial Advice, rather than a custom field. Host checks STAN + Repeat Indicator to recognize a message it may have already processed and responds idempotently — re-acknowledging without re-applying the Account change.

**Decline Reason**:
The specific cause of a Declined Transaction. v1 set: `Insufficient Funds`, `Invalid Account` (unknown PAN). Deliberately small, expected to grow (e.g. expired/restricted card) once Account models more than balance/limit.

## Transaction Types (v1 scope)

Authorization, Financial, Reversal. Settlement/batch and network management messages are out of scope for v1 — deferred, same tier as USB serial support in the Terminal App.

A Financial transaction reaches Host one of two ways: the online request/response pair, or a Financial Advice reporting one already approved offline by Terminal (see Floor Limit in [terminal/CONTEXT.md](../terminal/CONTEXT.md)). Authorization is online-only — no offline path.

## Concurrency (v1 scope)

Host processes Transactions single-threaded/synchronously — one Transaction (including its Account mutation) completes before the next begins. No locking or concurrent Account access. This is a deliberate non-goal, not an oversight: the project demonstrates protocol and decisioning logic, not concurrent systems design.

## Currency (v1 scope)

Single currency, AUD, for v1. DE 49 is still populated on the wire with a fixed AUD value for format fidelity, but domain logic doesn't branch on currency. Multi-currency Accounts are deferred — future scope, not a rejected idea.
